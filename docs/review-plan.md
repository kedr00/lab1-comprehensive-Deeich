### 2.2. Техническое задание

**Область применения.** Система управления базами данных (СУБД) предназначена для хранения и обработки данных микросервиса «Расчёт корзины и скидок» в системе лояльности. Микросервис обслуживает финансовые транзакции: расчёт стоимости корзины, начисление и списание баллов лояльности, применение промокодов и скидок по уровню клиента. Система должна обеспечивать надёжное хранение истории транзакций, баланса баллов и справочника промокодов при интенсивной конкурентной нагрузке.

**Бизнес-потребности.** Расчёт корзины и скидок — критичная финансовая операция, поэтому ключевое требование — строгая согласованность данных: начисление баллов и применение промокода должны выполняться атомарно, без частичного применения. Ошибка в расчёте ведёт к прямым финансовым потерям и претензиям клиентов. Также требуются целостность данных (уникальность промокодов, контроль баланса баллов, исключение отрицательных значений), производительность чтения при частых запросах истории транзакций, гибкость схемы при развитии продукта и приемлемая стоимость владения (открытый исходный код, наличие специалистов на рынке).

**Требования к ПО:**
- Обязательные: поддержка ACID-транзакций; целостность данных и ограничения (уникальность, внешние ключи, проверки); производительность чтения при большом объёме истории транзакций; открытая лицензия / низкая стоимость владения.
- Приоритетное: гибкость схемы данных при развитии продукта.

### 2.3. Выбор объектов анализа

Для сравнения выбраны две СУБД, соответствующие профилю задачи:

- **PostgreSQL** — реляционная СУБД с открытым исходным кодом. Полноценная поддержка ACID, строгие ограничения целостности (PRIMARY KEY, FOREIGN KEY, UNIQUE, CHECK), богатая экосистема, зрелость и большое сообщество. Широко используется в финансовых системах.
- **MongoDB** — документоориентированная NoSQL СУБД с открытым исходным кодом. Гибкая документная схема (BSON), горизонтальное масштабирование. Поддержка ACID-транзакций появилась в более поздних версиях и имеет ограничения по сравнению с реляционными СУБД.

### 2.4. Формирование критериев

Критерии сформулированы так, чтобы их можно было проверить объективно — по документации, наличию функции или результатам измерений.

| Критерий | Вес | Способ проверки |
|---|---:|---|
| Поддержка ACID-транзакций | 35 | Проверяется полнота поддержки атомарности, согласованности, изолированности, долговечности. Оценка 5 — полная нативная поддержка; 3 — поддержка с ограничениями |
| Целостность данных и ограничения | 25 | Проверяется наличие ограничений уникальности, внешних ключей, проверок значений. Оценка 5 — полный набор; 2 — ограниченный набор |
| Гибкость схемы | 15 | Проверяется возможность изменения структуры данных без миграций. Оценка 5 — schema-free; 3 — требует миграций |
| Производительность чтения | 15 | Проверяется скорость выборки истории транзакций и агрегатов. Оценка 5 — высокая; 4 — достаточная |
| Стоимость владения и экосистема | 10 | Проверяется наличие открытой лицензии, зрелость экосистемы, доступность специалистов. Оценка 5 — полностью открыто и зрело |
| **Итого** | **100** | |

**Сумма весов = 35 + 25 + 15 + 15 + 10 = 100 (в долях: 1.0).**

### 2.5. Таблица анализа

| Критерий | Вес | PostgreSQL | MongoDB | Обоснование оценки |
|---|---:|---:|---:|---|
| Поддержка ACID-транзакций | 35 | 5 | 3 | PostgreSQL: полная нативная ACID-поддержка на уровне ядра. MongoDB: поддержка есть, но с ограничениями (в кластере, накладные расходы) |

**Формула расчёта итогового балла (Excel):**

=СУММПРОИЗВ($B$2:$B$6; C2:C6) / 100

**Расчёт вручную:**

PostgreSQL = (35×5 + 25×5 + 15×3 + 15×4 + 10×5) / 100 = (175 + 125 + 45 + 60 + 50) / 100 = **4,55**

MongoDB = (35×3 + 25×2 + 15×5 + 15×4 + 10×4) / 100 = (105 + 50 + 75 + 60 + 40) / 100 = **3,30**

### 2.6. Анализ достоинств и недостатков

**PostgreSQL (4,55 балла)**

*Достоинства:*
- Полноценная нативная поддержка ACID-транзакций — критично для финансовых операций
- Строгие ограничения целостности: уникальность промокодов, внешние ключи, CHECK-ограничения на баланс баллов
- Мощные агрегатные запросы и JOIN для аналитики по истории транзакций
- Зрелая экосистема, большое сообщество, много специалистов на рынке
- Открытая лицензия, отсутствие затрат на лицензию

*Недостатки:*
- Менее гибкая схема — изменения требуют миграций
- Горизонтальное масштабирование сложнее, чем в документных СУБД

**MongoDB (3,30 балла)**

*Достоинства:*
- Гибкая документная схема — удобно при быстром развитии продукта
- Хорошее горизонтальное масштабирование
- Высокая скорость чтения целых документов
- Открытая лицензия

*Недостатки:*
- Поддержка ACID-транзакций ограничена по сравнению с реляционными СУБД
- Слабые ограничения целостности — валидация переносится на уровень приложения
- Меньше специалистов на рынке для финансового домена

**Заключение по разделу.** По результатам анализа **PostgreSQL признан оптимальным решением** (4,55 балла из 5). СУБД набрала максимальные оценки по двум ключевым для финансовой задачи критериям — ACID (35%) и целостность данных (25%). Ошибка в атомарности начисления баллов или применении промокода ведёт к прямым финансовым потерям, поэтому эти критерии имеют наибольший вес. **Рекомендация:** использовать PostgreSQL. MongoDB (3,30) — альтернатива только при приоритете гибкости схемы, но её ограничения по ACID и целостности — существенный риск для финансового домена.

## 5. Обратное проектирование и планирование ревью

### 5.1. Анализ алгоритма

![UML Diagram](docs/uml_diagram.png)

Диаграмма деятельности отражает: начальный и конечный узлы; условие базовой скидки `cart_sum > 15000`; цикл перебора промокодов с вложенными условиями `SUMMER` / `VIP`; условия по уровню лояльности `tier == 1` / `tier == 2`; финальное ограничение максимальной скидки `price < cart_sum * 0.70`.

**Выявленные «запахи кода» (Code Smells):**
- **Магические числа:** 15000, 0.85, 500, 0.90, 0.97, 0.93, 0.70 — должны быть именованными константами.
- **Отсутствие валидации входных данных:** не проверяются `cart_sum >= 0`, допустимые значения `tier`, тип `promos`.
- **Смешение ответственности:** логика скидок, промокодов и уровня лояльности в одной функции.
- **Хрупкость порядка применения:** порядок применения промокодов и скидок неявно задан последовательностью кода.
- **Нет обработки неизвестных промокодов:** неизвестный промокод молча игнорируется.

### 5.2. План code-review

**Ссылка на открытый PR:** [https://github.com/kedr00/lab1-comprehensive-Deeich/pull/4]

Подход к ревью: проверка финансовой логики модуля `src/discount.py` с акцентом на точность расчётов, защиту от фрода и корректность применения скидок.

**Цели ревью:** точность расчётов, защита от фрода, корректность применения скидок и промокодов.

**Ключевые измеримые критерии:**
- Отсутствие магических чисел (именованные константы)
- Наличие валидации входных параметров
- Покрытие тестами > 80%
- Соответствие линтеру (нет неиспользуемых импортов, длина строки ≤ 80)

**Участники и роли:** автор (разработчик модуля), ревьюер (Tech Lead — владелец кода), наблюдатель (QA-инженер).

**Механизм эскалации:** при разногласиях — автор → ревьюер → Tech Lead в течение 24 часов; окончательное решение принимает Tech Lead и фиксирует в комментарии PR.

Полный текст плана: [`docs/review-plan.md`](docs/review-plan.md).

## 6. Заключение

Настроенные процессы снижают риск внесения дефектов в финансовую логику за счёт нескольких барьеров:

1. **Обоснованный выбор технологии** — PostgreSQL обеспечивает ACID и целостность, критичные для транзакций и баллов.
2. **Защита ветки `develop`** и обязательный Pull Request исключают прямые несогласованные изменения.
3. **CODEOWNERS** гарантирует обязательный аппрув владельца кода.
4. **CI-линтер flake8** автоматически отлавливает дефекты стиля и неиспользуемый код до слияния (продемонстрировано на Quality Gate).
5. **План code review с измеримыми критериями** и механизмом эскалации делает проверку воспроизводимой и прозрачной.
6. **UML-диаграмма и анализ code smells** выявили конкретные точки риска в legacy-алгоритме для последующего рефакторинга.

Совокупность этих мер обеспечивает контролируемый и воспроизводимый процесс разработки микросервиса.
